# Parallel Batch Image Processor

A Java-based desktop application that applies a filter pipeline (Gaussian Blur followed by Sobel Edge Detection) to batches of high-resolution images. The project implements both sequential and parallel processing strategies to analyze performance speedup.

## Project Overview
The application provides three processing modes:
The application provides three processing modes:
- **Sequential**: Single-threaded baseline.
- **Parallel Images**: Distributes different images across a fixed thread pool.
- **Parallel Strips**: Splits a single image into horizontal strips processed in parallel using a dedicated ForkJoinPool.

**Speedup** is calculated as `T_sequential / T_parallel`. The application features a responsive Swing UI that remains active and never freezes during heavy computation.

## Requirements
- **OS**: Windows
- **Java**: 
    - The runnable JAR requires **Java 17+** (compiled with `maven.compiler.release=17`).
    - Benchmarks are designed to be run with **Java 21.0.9**.

## Build Instructions
Build the project using the IntelliJ Maven tool window:
`Lifecycle` -> `package`

**Output JAR**: `target\parallel-image-processor-1.0-SNAPSHOT.jar`

*Note: `mvnw` is not used in this environment; build via the IDE. The `maven-surefire-plugin` is configured with `forkCount=0` because Surefire forking fails in this environment; the resulting warning is harmless.*

## Running the Application
You can launch the application in two ways:
1. **Double-click `run_app.cmd`**: Launches the app using `javaw` with a 4GB heap limit (`-Xmx4G`).
2. **Command Line**: Run `java -jar target\parallel-image-processor-1.0-SNAPSHOT.jar`.

### UI Guide
- **Folders**: Select input and output directories.
- **Mode**: Choose between Sequential, Parallel Images, or Parallel Strips.
- **Threads**: Set the number of worker threads (disabled for Sequential mode).
- **Compare**: Enable to run a sequential baseline before the selected mode to calculate speedup.
- **Start/Cancel**: Begin processing or interrupt a running task.
- **Results**: Displays elapsed time, speedup, efficiency (0-1), and processing counts.

**Notes**:
- **Output**: Resulting images are Sobel edge maps (white edges on a black background), which is the expected output.
- **Efficiency**: Displayed as a decimal between 0 and 1.
- **Baseline Cache**: The sequential baseline is cached based on the canonical input path, image count, and total file size. Modifying images in-place without changing their size will not trigger a cache refresh.
- **Folders**: It is permissible to create the output folder inside the input folder.
- **Illustrative Run**: The UI provides a single illustrative run. Official performance numbers for the report are generated by the benchmark harness.

## Benchmarks
Run the benchmark suite by executing `run_benchmarks.cmd`.
- **Execution**: The script generates 25 images (3840x2160) in `./dataset` and runs the `BenchmarkHarness` three times with identical arguments (`--dataset ./dataset --out results.csv --mode COMPUTE_ONLY`). Each harness invocation is its own JVM process.
- **Verification**: The sequential run writes golden checksums to `golden_checksums.txt` (current working directory); parallel runs are verified against them.
- **Results**: Each harness run writes `<out>_<timestamp>.csv` in the current directory. With `--out results.csv` the file is named `results.csv_<timestamp>.csv`, which does not match the `results_*.csv` rule in `.gitignore`. Valid results are moved by hand to `results/`.
- **Note**: This script is a quick smoke run to verify the harness; it is NOT the final experiment.

- `com.homework.processor.ui`: Swing-based user interface and worker threads.

## Thread Safety Summary
- **Pools**: Uses a fixed thread pool for images and a dedicated ForkJoinPool for strips.
- **Memory**: A `Semaphore` bounds the number of images decoded into memory simultaneously.
- **Progress**: Tracking is handled via `AtomicInteger`.
- **Cancellation**: Uses a `CancelToken` to signal threads to stop.
- **Data Integrity**: Threads write to disjoint regions of the output array; input buffers are treated as immutable; processors are stateless.
